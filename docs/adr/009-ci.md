# 009. CI: GitHub Actions로 PR마다 백엔드·프론트 검사

- 상태: 확정
- 날짜: 2026-10-28
- 관련: [ADR 006](006-batch-execution.md) (배포·CronJob은 8단계), [ADR 008](008-frontend-structure.md) (`schema.d.ts` 커밋 규칙)

## 결정 요약

| 항목 | 결정 |
|---|---|
| 도구 | GitHub Actions (`.github/workflows/ci.yml`) |
| 실행 시점 | `main` 대상 PR, `main` push |
| job | `backend`(`./gradlew test`), `frontend`(`npm ci` → lint → test → build). 서로 기다리지 않고 동시에 돈다 |
| 경로 필터 | 두지 않는다. 변경 범위와 상관없이 두 job을 매번 돌린다 |
| 취소 | 같은 PR에 새 커밋이 오면 이전 실행을 취소한다. `main` push는 취소하지 않는다 |
| 버전 | Java는 `setup-java`에 17, Node는 `frontend/.nvmrc`를 로컬과 CI가 같이 읽는다 |
| 머지 조건 | `main` 보호 규칙에 두 job을 필수 검사로 지정한다. 승인 인원은 요구하지 않는다 |
| 범위 밖 | Docker 이미지, 배포(7·8단계), `schema.d.ts` 최신 여부 검사(별도 PR) |

---

## 1. 배경

지금까지 "모든 커밋에서 테스트가 통과해야 한다"는 규칙을 로컬 실행으로만 지켰다. 백엔드·프론트 테스트(각각 180여 개)를 PR마다 사람이 돌렸고, 빠뜨려도 막을 장치가 없었다. 개발은 Windows에서 하지만 배포 대상은 Linux라, Windows에서만 통과하는 문제도 드러나지 않았다 (아래 ③).

## 2. 결정 근거

### ① GitHub Actions

저장소가 GitHub에 있고 public이라 사용량 제한이 없다. 별도 서버(Jenkins 등)를 운영할 이유가 없다. 8단계 배포에서도 이미지 빌드를 같은 워크플로에 붙이면 된다.

### ② job 분리, 경로 필터 없음

- 백엔드와 프론트는 의존성·도구가 달라 job을 나눈다. 동시에 돌아서 전체 시간은 둘 중 긴 쪽(백엔드, Testcontainers 이미지 받기 포함)으로 정해진다
- 경로 필터(`paths:`)를 두면 프론트만 바꾼 PR에서 `backend` job이 아예 생기지 않는다. 그 job을 필수 검사로 지정해 두면 PR이 "결과 대기"로 묶여 머지할 수 없다. 우회 방법(필터 job + 조건부 step)은 구성이 복잡해지는 데 비해 아끼는 시간이 몇 분이라 쓰지 않는다
- 통합 테스트는 Testcontainers가 러너의 Docker로 `postgis/postgis:17-3.5`를 띄운다. 로컬과 같은 경로라 CI용 DB 설정(서비스 컨테이너)을 따로 두지 않는다

### ③ Windows에서 드러나지 않던 차이를 고정한다

- **`gradlew` 실행 권한**: git에 `100644`로 들어 있었다. Windows는 실행 권한을 보지 않아 몰랐고, Linux 러너에서는 `./gradlew`가 Permission denied로 실패한다. `git update-index --chmod=+x`로 `100755`로 바꿨다
- **컴파일 인코딩**: JDK 17의 Windows 기본 인코딩은 MS949다. 소스의 한글 주석·`@Schema` 설명이 PC 설정에 따라 깨질 수 있어 `options.encoding = 'UTF-8'`로 고정했다. OpenAPI 문서(→ `schema.d.ts`)가 OS와 상관없이 같아진다
- **Node 버전**: `frontend/.nvmrc` 한 곳에 두고 CI는 `node-version-file`로 읽는다

### ④ 취소 범위

PR은 마지막 커밋의 결과만 의미가 있어 이전 실행을 취소한다. `main` push까지 취소하면 PR을 연달아 머지할 때 앞 커밋의 결과가 남지 않아, 어느 커밋에서 깨졌는지 알 수 없다.

### ⑤ 필수 검사만, 승인은 요구하지 않음

혼자 쓰는 저장소라 "승인 1명 필요"를 켜면 자기 PR을 승인할 수 없어 머지가 막힌다. 필수 검사만 지정하고, 머지 방식은 squash만 허용한다 (PR = 검토 단위).

## 3. 한계

- 빌드 chunk 크기 경고(500 kB)는 실패로 보지 않는다. 코드 분할은 배포 때 검토한다
- 백엔드 job은 매번 postgis 이미지를 받는다 (수백 MB). 느려지면 이미지 캐시를 검토한다
- 액션은 메이저 태그(`@v7` 등)로 적는다. 커밋 SHA 고정보다 공급망 공격에 약하지만, 공식 `actions/*`·`gradle/actions`만 쓰고 권한은 `contents: read`로 제한한다

## 4. 재검토 조건

- CI 시간이 10분을 넘기면: 경로 필터 + 필수 검사 우회 구성, 이미지 캐시
- 8단계 배포를 시작하면: 이미지 빌드·푸시 job 추가, 권한(`packages: write`) 범위 재검토
- 협업자가 생기면: 승인 요구 규칙
