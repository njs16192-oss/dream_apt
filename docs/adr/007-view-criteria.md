# 007. 조회 기준: 면적 그룹 정수 반올림, 일괄 거래 같은 날 10건 이상, `valid_apt_trade` 뷰

- 상태: 확정
- 날짜: 2026-10-25
- 관련: [ADR 002](002-trade-data-schema.md) (유효 거래 정의를 3단계에서 정하기로 함), [ADR 004](004-trade-reconcile.md) (같은 키 여러 행, `missing_since`), [ADR 005](005-collect-schedule.md) (재조회 기간), [조회 설계 전 데이터 분석](../analysis/2026-10-view-analysis.md), [계약→등기·해제 지연 분석](../analysis/2026-10-data-lag.md)

## 결정 요약

| 항목 | 결정 |
|---|---|
| 면적 그룹 | `area_group = ROUND(exclu_use_ar)` (정수 ㎡, HALF_UP). 단지 안 다른 면적과 상관없이 값만으로 정한다 |
| 일괄 거래 | 같은 단지·같은 계약일 **유효 거래 10건 이상**이면 그 거래들을 `is_bulk = true`. 전 기간 같은 기준 |
| 일괄 거래 처리 | 삭제하지 않고 표시만 한다. **요약값·정렬·통계는 일괄 거래 제외, 개별 거래 나열은 포함**(`is_bulk` 표시) |
| 일괄 거래 위주 단지 | 유효 거래의 80% 이상이 `is_bulk`인 단지는 단지 단위로 안내한다 |
| 구현 | 일반 뷰 `valid_apt_trade` (유효 거래 + `sgg_cd` + `area_group` + `is_bulk`). 윈도는 `PARTITION BY sgg_cd, apt_seq, deal_date`. 대표 쿼리 최대 67ms로 100ms 기준 안이라 **일반 뷰를 유지**한다 |
| 월별 가격 | 중앙값(`percentile_cont(0.5)`, 만원 정수로 **HALF_UP** 반올림) + 거래 건수를 같이 준다 |
| 미완성 월 | 기준일(서울 날짜)이 속한 달과 그 전 달, **최근 2개월은 "집계 중"** 으로 표시한다 |
| 단지 검색 | `pg_trgm`. 검색 결과에 구·동·준공연도를 포함한다 |

## 1. 배경

3단계에서는 저장된 거래를 단지·면적별 가격 추이, 구별 거래량, 거래 목록으로 보여준다. 그러려면 세 가지를 먼저 정해야 한다.

- **어떤 거래를 셀지.** ADR 002·004에서 유효 거래(`cancelled = false AND missing_since IS NULL`)를 정했지만, 일괄 거래를 어떻게 다룰지는 정하지 않았다
- **면적을 어떤 단위로 묶을지.** API는 전용면적(㎡, 소수 둘째 자리)만 준다. 같은 타입이 84.95 / 84.98 / 84.99처럼 갈라져 온다
- **최근 데이터를 어떻게 보여줄지.** 계약 후 신고·해제가 늦게 반영되므로 최근 달은 숫자가 계속 바뀐다

[조회 설계 전 데이터 분석](../analysis/2026-10-view-analysis.md)(서울 25개 구, 유효 거래 355,502건)의 수치를 근거로 정한다.

## 2. 결정 근거

### ① 면적 그룹: R1 정수 반올림

| 규칙 | 갈라짐 (<0.5㎡ 쌍) | 갈라짐 (<0.1㎡ 쌍) | 합쳐짐 (≥0.5㎡ 쌍) | 데이터가 늘 때 기존 그룹 |
|---|---:|---:|---:|---|
| R0 원값 | 7,821 | 3,515 | 0 | 안 바뀜 |
| **R1 정수 반올림** | 970 | **51** | 419 | **안 바뀜** |
| R2 정수 버림 | 656 | 105 | 938 | 안 바뀜 |
| R3 근접 묶기 (<0.5㎡) | 0 | 0 | 533 | 범위가 바뀌는 단지 2.4%, 합쳐지는 단지 0.1% |
| R3 근접 묶기 (<1.0㎡) | 0 | 0 | 2,866 | 범위가 바뀌는 단지 3.1%, 합쳐지는 단지 0.1% |

- **선택 기준은 안정성이다.** 면적 그룹은 URL(`/complexes/{aptSeq}/areas/85`), 차트 시리즈, 관심 단지 알림의 키가 된다. 키가 바뀌면 저장된 링크와 알림 설정이 다른 면적을 가리키거나 깨진다
- **R3는 갈라짐이 가장 적지만 키가 안정적이지 않다.** 단지 안 다른 면적 값에 따라 그룹이 정해지므로, 새 면적이 처음 거래되면 기존 그룹의 범위가 바뀐다. 2025년 말 → 2026-10 사이에만 단지의 2.4–3.1%에서 바뀌었고, 0.1%에서는 두 그룹이 하나로 합쳐졌다 (디큐브시티 [59.16] / [59.84–59.95]에 59.60이 들어와 합쳐짐). 또 R3(<1.0㎡)는 연쇄로 폭이 6.40㎡까지 넓어진다
- **R2(정수 버림)는 경계가 흔한 면적에 걸린다.** 국민평형 85㎡ 근처에서 84.99 / 85.00, 84.97 / 85.00이 갈라진다. 0.1㎡ 미만 갈라짐이 R1의 두 배(105쌍)이고, 다른 타입일 수 있는 쌍을 합치는 수도 R1의 두 배(938쌍)다
- **R1은 값만으로 정해져서 데이터가 늘어도 바뀌지 않고, 표시값("85㎡")이 곧 키다.** 사람들이 부르는 "84㎡·59㎡"와 1㎡ 차이가 날 수 있지만, 표시 문구는 화면에서 정할 문제로 남긴다
- PostgreSQL `ROUND(numeric)`은 0.5를 0에서 먼 쪽으로 올린다. 면적은 양수라서 HALF_UP과 같다 (분석 스크립트와 같은 규칙)

### ② 일괄 거래: 같은 단지·같은 계약일 유효 거래 10건 이상 (C2), 전 기간

| 기준 | 걸린 거래 | 일반 거래처럼 보이는 그룹 (2021-11+) | 2024+에서 필드 기준(C3∪C4)과 겹침 |
|---|---:|---:|---|
| C1 같은 날 ≥5건 | 8,729 | 51% (170/334) | C1 중 71.9% / C3∪C4 중 97.0% |
| **C2 같은 날 ≥10건** | 6,186 | **4.5% (4/89)** | **C2 중 97.7% / C3∪C4 중 94.3%** |

C3 = 같은 날 직거래 ≥3건, C4 = 같은 날 법인·공공기관이 낀 거래 ≥3건.

- **같은 날 10건 이상은 성격이 다른 집단이다.** 직거래 90%, 2024년 이후 분은 개인→개인 2.3%(법인→공공기관 67%, 법인→법인 23%)다. 5–9건은 개인→개인 93%로 일반 거래에 가깝다. 그래서 5건(C1)이 아니라 10건으로 자른다. C1은 대단지에 거래가 몰린 날(파크리오 2025-03-22 16건, 모두 중개·개인 간)을 많이 잡는다
- **C3·C4를 최근 데이터에만 더하지 않는다.** `dealing_gbn`은 2021-11, `buyer_gbn`·`seller_gbn`은 2024-01부터만 값이 있다. 이 필드를 쓰는 기준을 그 기간에만 더하면 2021-11·2024-01을 경계로 걸러지는 양이 갑자기 달라지고, 거래량 시계열에 **실제 시장과 상관없는 가짜 변화**가 생긴다. 2024년 이후에서 C2와 C3∪C4가 94–98% 겹치므로, 기준을 하나로 통일해서 잃는 정확도가 작다. **최근 데이터의 정확도보다 기간 간 일관성을 우선한다**
- **삭제하지 않고 표시한다.** 일괄 거래도 실제로 일어난 거래이고, 판별 기준은 휴리스틱이라 틀릴 수 있다. 원본은 그대로 두고 조회 시점에 `is_bulk`로 구분한다
- **거래량·가격 추이는 기본 제외, 거래 목록에는 포함한다.**
  - 거래량은 일괄 거래에 크게 흔들린다. 걸러내면 구×월 셀의 5.3%가 바뀌고 56셀은 20% 넘게 준다 (금천구 2022-11 146 → 11건). 일괄 매각 하루가 그 구의 시장 거래량처럼 보이지 않게 한다
  - 가격 중앙값은 거의 안 바뀐다(셀의 0.02%). 일괄 거래는 대부분 거래가 그날뿐인 단지에서 일어나기 때문이다. 그래도 기준을 거래량과 같게 해서 "추이 = 일괄 제외"로 통일한다
  - 거래 목록은 "무슨 일이 있었나"를 보여주는 곳이라 숨기지 않고 일괄 거래 표시를 붙인다
- **일반 규칙: 요약값·정렬·통계는 일괄 거래 제외, 개별 거래 나열은 포함.** 거래 여러 건을 하나의 숫자로 줄이거나 그 숫자로 순서를 정하는 곳(중앙값, 건수, 최근 거래가, 검색 정렬)은 모두 제외하고, 거래를 한 건씩 보여주는 곳만 포함한다. 예:
  - 검색 결과의 최근 거래 수(정렬 기준): 제외. 일괄 매각 단지가 검색 결과 위로 올라오지 않게 한다
  - 단지 상세의 면적 그룹별 거래 수·마지막 거래일·마지막 거래 금액: 제외. 일괄 거래 건수는 따로 준다
  - 구 월별 거래량: 제외. 월별 일괄 거래 건수는 따로 준다
  - 단지·면적 거래 목록: 포함, 건마다 일괄 여부 표시
- **일괄 거래 위주 단지는 단지 단위로 안내한다.** C2 기준 유효 거래의 80% 이상이 일괄 거래인 단지가 90개(5,715건)다. 대부분 신축의 하루짜리 일괄 매각이다 (에드가휘경 313건, 세이지움태릉입구역 278건). 이런 단지는 걸러내면 추이가 비고, 안 걸러내면 추이가 일괄 거래 값이 된다. 차트 대신 "이 단지의 거래는 대부분 일괄 거래" 안내를 보여준다. 이 비율은 저장하지 않고 같은 뷰에서 계산한다

### ③ 구현: 일반 뷰 `valid_apt_trade`로 시작

```sql
CREATE VIEW valid_apt_trade AS
SELECT t.*,                      -- 컬럼 목록은 구현 때 명시한다
       c.sgg_cd,
       ROUND(t.exclu_use_ar)::int AS area_group,
       COUNT(*) OVER (PARTITION BY c.sgg_cd, t.apt_seq, t.deal_date) >= 10 AS is_bulk
FROM apt_trade t
JOIN apt_complex c ON c.apt_seq = t.apt_seq
WHERE t.cancelled = false AND t.missing_since IS NULL;
```

(Flyway 마이그레이션 파일로 만든다)

- **유효 거래 조건을 한 곳에 둔다.** 모든 조회가 이 뷰를 쓰면 "유효 거래 = ..." 조건과 일괄 기준을 쿼리마다 반복하지 않는다. 기준을 바꿀 때 뷰 하나만 고친다
- **`is_bulk`는 유효 거래만으로 센다.** 같은 날 거래 중 일부가 해제되면 10건 아래로 내려가 `is_bulk`가 풀릴 수 있다. 해제된 거래가 일괄 판단에 섞이지 않게 하기 위한 것이다
- **일반 뷰로 시작하는 이유**: 수집이 매일 데이터를 바꾸므로, 일반 뷰는 따로 갱신할 필요가 없다. materialized view는 갱신 시점·실패 처리를 배치에 더해야 한다

#### 윈도 파티션에 `sgg_cd`를 넣는 이유

PostgreSQL은 윈도 함수가 있는 뷰(서브쿼리)에 바깥 조건을 밀어 넣을 때, **조건이 모든 `PARTITION BY` 컬럼에만 걸려 있으면** 윈도 계산 전에 거른다. 파티션 하나는 통째로 남거나 통째로 빠지므로 윈도 결과가 바뀌지 않기 때문이다. 그 밖의 조건은 윈도를 전체 행에 대해 계산한 뒤에 적용한다.

- 초안 정의(`PARTITION BY apt_seq, deal_date`, 뷰에 `sgg_cd` 없음)로는 구 단위 조회가 유효 거래 전체(355,502행)에 윈도를 계산한 뒤 구를 거른다
- 단지가 정해지면 구도 정해지므로(`apt_complex.apt_seq` → `sgg_cd`) `PARTITION BY sgg_cd, apt_seq, deal_date`는 같은 파티션을 만든다. 결과는 같고, `sgg_cd`·`apt_seq`·`deal_date` 조건을 뷰 안으로 밀어 넣을 수 있다
- `area_group`·`is_bulk` 조건은 파티션 키가 아니라서 밀려 들어가지 않는다. 같이 쓰는 `apt_seq`·`sgg_cd` 조건이 먼저 걸러 주므로 문제 되지 않는다

#### 측정 결과 (2026-10-25, 로컬 Docker, 유효 거래 355,502건)

결과 동일성: 초안 정의(A)와 `sgg_cd` 파티션 정의(B)의 `(id, area_group, is_bulk)`를 양방향 `EXCEPT`로 비교해 **차이 0행**이다 (두 정의 모두 355,502행, `is_bulk` 6,186행 = 분석 문서 C2와 같음).

대표 쿼리는 트랜잭션 안에 두 뷰를 임시로 만들어 `EXPLAIN (ANALYZE, BUFFERS)`로 5번씩 실행했다 (실행 시간 ms, 모두 공유 버퍼 적중 상태). 대상은 거래가 가장 많은 단지(파크리오 `11710-6266`)와 가장 많은 구(노원구 `11350`, 유효 거래 31,802건)다.

| # | 대표 쿼리 | A (초안) | **B (`sgg_cd` 파티션)** |
|---|---|---:|---:|
| 1 | 단지 하나 × 면적 그룹 하나(85)의 월별 중앙값·건수, 전 기간, 일괄 제외 | 1.5–1.8 | **2.0–2.8** |
| 2 | 구 하나의 월별 거래량, 전 기간, 일괄 제외 | 299–304 | **63–67** |
| 2′ | 같은 쿼리, 최근 3년(`deal_date >= 2023-10-01`) | – | **40–49** |
| 3 | 단지 하나의 최근 거래 50건 | 1.2–1.6 | **1.9–2.3** |
| 4 | 단지 하나의 일괄 거래 비율 (에드가휘경 `11230-4330`) | 0.17–0.19 | **0.22–0.28** |

- **A는 2번이 100ms를 넘는다** (약 300ms). 계획에서 WindowAgg가 355,502행 전체를 처리하고, 그 뒤에 구 조건으로 거른다
- **B는 구 조건이 윈도 전에 들어간다.** `apt_complex` 스캔에 `sgg_cd = '11350'`이 걸리고(317단지), 조인 결과 31,802행에만 윈도를 계산한다. 2′에서는 `deal_date` 조건도 `apt_trade` 스캔의 Filter로 들어간다
- B는 조인이 하나 늘어서 단지 단위 쿼리(1·3·4)가 0.1–1ms 느려지지만, 모두 3ms 안이다
- **결정: B로 일반 뷰를 만든다.** 대표 쿼리 최대 67ms로 전환 기준(100ms) 안이다
- **남은 위험**: 2번의 남은 비용은 `apt_trade` 전체 병렬 seq scan(프로세스 3개가 나눠 읽어 약 17ms)과 정렬·윈도 계산(약 30ms)이다. 구 하나를 조회해도 테이블 전체를 읽으므로, **수집 지역이 늘면 구 하나의 조회 시간도 전체 데이터 크기에 비례해 늘어난다.** 전국으로 넓히면 이 쿼리부터 다시 잰다

전환 기준(변경 없음): 위 대표 쿼리 중 하나라도 실행 시간 **100ms를 넘으면** materialized view로 바꾼다. 바꾸면 수집 Job이 끝난 뒤 `REFRESH MATERIALIZED VIEW CONCURRENTLY`로 갱신한다 (unique 인덱스 필요). 그 전에 구 단위 쿼리용 인덱스(예: `apt_trade`에 구 코드 컬럼 추가 후 인덱스)로 해결되는지 먼저 본다.

### ④ 월별 가격: 중앙값 + 거래 건수

- 평균은 고가·저가 거래 하나에 크게 끌린다. 단지·면적·월 셀은 거래가 적어서(그룹의 절반 이상이 전체 기간 5건 미만) 영향이 더 크다. 중앙값을 쓴다
- `percentile_cont(0.5)`는 짝수 건이면 가운데 두 값의 평균이다. `percentile_disc`는 실제 거래 금액 중 하나를 고르지만, 2건일 때 낮은 쪽을 고르는 편향이 있다
- **응답은 만원 단위 정수로 HALF_UP 반올림한다** (x.5 → 올림). 금액은 양수라서 "0에서 먼 쪽"과 같다
  - **주의**: `percentile_cont`는 `double precision`을 돌려주고, PostgreSQL의 `ROUND(double precision)`은 **짝수 쪽으로 반올림(half-to-even)** 한다. 로컬 확인: 100,000·100,005의 중앙값 100,002.5가 `ROUND(...)`로 **100,002**, `ROUND(...::numeric)`으로 **100,003**이다. 그래서 반드시 `numeric`으로 바꾼 뒤 반올림한다
  - SQL: `ROUND((percentile_cont(0.5) WITHIN GROUP (ORDER BY deal_amount))::numeric)::int`
  - 짝수 건의 두 금액이 둘 다 정수(만원)라서, 평균의 소수 부분은 0 또는 0.5뿐이다. 부동소수 오차로 x.5가 x.4999…가 되는 경우는 없다
- **거래 건수를 같이 준다.** 1건짜리 달의 중앙값은 그 거래 하나의 금액이다. 화면이 건수를 보고 신뢰도를 표시하거나 점 크기를 다르게 할 수 있게 한다. 몇 건 미만은 숨기는 식의 판단은 API가 하지 않는다

### ⑤ 미완성 월: 최근 2개월 "집계 중"

기준일(서울 날짜, ADR 005와 같음)이 속한 달 M과 M-1을 "집계 중"으로 표시한다. 값은 주되, 바뀔 수 있다는 표시를 붙인다.

[지연 분석](../analysis/2026-10-data-lag.md) 근거:
- **신규 신고**: 계약 후 30일 안에 신고해야 하므로 계약월 M은 M+1월 말까지 대부분 들어온다. 기준일이 M+1에 있는 동안은 M이 아직 덜 찼다 → M, M-1은 미완성
- **해제**: M+1월 말까지 66.7%, M+2월 말까지 87.1%가 일어난다 (사건 날짜 기준). M-2를 처음 "완성"으로 보여주는 시점(기준일이 M-2+2월)에 남은 해제는 전체 해제의 약 1/3이다. 해제 비율이 거래의 약 5%라서 거래 수로는 약 1.6%가 나중에 빠진다
- **등기**는 가격·거래량에 영향이 없다 (등기일은 표시 정보)
- N = 3으로 하면 남은 해제가 약 0.6%로 줄지만, 가장 관심 있는 최근 석 달이 모두 "집계 중"이 된다. 거래 수가 2% 안쪽으로 바뀌는 정도는 "완성"으로 보여준다
- 이 기간의 `is_bulk`도 바뀔 수 있다. 같은 날 거래가 늦게 신고되면서 9건 → 10건이 될 수 있기 때문이다

### ⑥ 단지 검색: `pg_trgm`, 결과에 구·동·준공연도

- **같은 이름 단지가 많다.** 단지명이 두 단지 이상에 쓰이는 경우가 전체 단지의 19.4%(이름 543개)이고, 같은 구 안에서도 154개 이름이 겹친다 ("현대" 30단지, "삼성" 21단지). 이름만 보여주면 고를 수 없으므로 검색 결과에 구·법정동·준공연도를 넣는다
- **`pg_trgm`은 띄어쓰기·일부 오타에 강하다.** 단지명은 띄어쓰기 없이 오지만 사용자는 "헬리오 시티"처럼 친다. 로컬 확인: `similarity('헬리오시티', '헬리오 시티') = 0.44`로 기본 임계값 0.3을 넘는다. 이 DB 로캘에서 한글도 trigram으로 나뉜다
- **지금 규모에서는 인덱스가 속도에 꼭 필요하지는 않다.** 단지 8,591개에 `name ILIKE '%현대%'`를 seq scan으로 해도 3.4ms다. 그래도 인덱스(GIN, `gin_trgm_ops`)를 만드는 것은 수집 지역이 늘어날 때(전국 단지 수만 개)를 대비한 것이다
- 두 글자 검색어는 trigram 인덱스를 쓰지 못한다 (아래 "한계")
- 확장은 Flyway 마이그레이션에서 `CREATE EXTENSION IF NOT EXISTS pg_trgm`으로 만든다 (`postgis/postgis` 이미지에 포함되어 있음, 버전 1.6)

## 3. 한계

- **R1은 x.5 경계에서 거의 같은 면적을 가른다.** 0.1㎡ 미만 차이인데 다른 그룹이 되는 쌍이 51개다 (래미안대치팰리스 94.49 / 94.50 / 94.51, 우물골2단지두산위브 84.49 / 84.51). 같은 타입이 두 그룹으로 나뉘어 각 그룹의 거래 수가 줄어든다
- **같은 그룹 안에 다른 타입이 섞일 수 있다.** 0.5㎡ 이상 차이 나는 419쌍이 한 그룹이다. API에 타입 정보가 없어서 알 수 없다
- **일괄 기준은 휴리스틱이다.** 10건 이상인데 일반 거래로 보이는 그룹이 4개 있고(2021-11 이후), 10건 미만인데 일괄 거래로 보이는 2–4건 그룹이 85개(170건) 있다. 법인이 같은 날 2–3세대를 직접 판 경우는 잡지 못한다
- **2021-11 이전 일괄 거래는 필드로 검증할 수 없다.** C2와 필드 기준이 잘 겹친다는 것은 2024년 이후 데이터로 확인한 것이다. 과거에도 같다고 가정한다
- **`is_bulk`는 나중에 바뀔 수 있다.** 조회 시점의 유효 거래로 계산하므로, 같은 날 거래가 늦게 신고되면 9건 → 10건이 되어 `true`로, 일부가 해제되면 10건 → 9건이 되어 `false`로 바뀐다. 이미 보여준 거래의 일괄 여부와 가격 추이·거래량이 소급해서 달라진다. **5단계 신고가 알림을 설계할 때 고려해야 한다** (예: 일괄 거래로 판정되기 전 신고가로 알림이 나갔다가, 나중에 그 거래가 일괄 거래가 되는 경우)
- **미완성 월 N = 2는 신고 지연을 실측하지 않은 값이다.** 법정 기한(계약 후 30일)에 기댄다 (ADR 005 한계와 같음)
- **한글 두 글자 검색은 trigram 인덱스를 못 쓴다.** "현대", "삼성" 같은 두 글자 검색어는 trigram이 나오지 않아 GIN 인덱스가 후보를 줄이지 못하고 사실상 전체를 읽는다. 단지명은 두 글자짜리 흔한 이름이 많다. 지금 규모(단지 8,591개, seq scan 3.4ms)에서는 문제없다. 수집 지역을 늘릴 때 다시 재고, 느리면 다른 방식(예: 접두 검색용 B-tree `text_pattern_ops` 인덱스, 초성·별칭 검색 테이블)을 검토한다
- 서울 데이터만 봤다

## 4. 재검토 조건

- **뷰 성능**: ③의 대표 쿼리가 100ms를 넘으면 materialized view로 바꾸고, 측정 결과를 이 문서에 적는다. 수집 지역을 늘릴 때 다시 잰다 (구 단위 거래량 쿼리가 전체 테이블 크기에 비례하므로 이것부터)
- **단지 검색**: 수집 지역을 늘릴 때 두 글자 검색어의 실행 시간을 다시 잰다
- **면적 경계 갈라짐**: 사용자가 단지 화면에서 같은 타입이 두 면적으로 갈라져 보인다고 느끼면, 단지별 예외 매핑(수동 별칭)을 검토한다. 규칙 자체는 키 안정성 때문에 바꾸지 않는다
- **미완성 월**: 자동 수집이 3개월 이상 쌓이면(2027-01 이후) `created_at − deal_date`로 신규 신고 지연을 실측해서 N을 다시 본다 (ADR 005 재검토와 같은 시점)
- **일괄 기준**: 수집 지역이 늘어나면(신도시 대단지, 지방) 같은 날 10건 이상 분포와 C3∪C4 겹침을 다시 잰다
