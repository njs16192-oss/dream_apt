# 011. 인증·관심단지·신고가 알림: 서버 세션(DB 저장) + 자체 계정 + 화면 안 알림

- 상태: 확정
- 날짜: 2026-11-05
- 관련: [ADR 004](004-trade-reconcile.md) (해제·`missing_since`), [ADR 006](006-batch-execution.md) (Job 종료 코드는 수집 step 기준), [ADR 007](007-view-criteria.md) (면적 그룹·`is_bulk`·`valid_apt_trade`), [ADR 010](010-geocoding.md) (수집 Job의 지오코딩 step)

## 1. 배경

5단계에서 로그인한 사용자가 단지를 관심단지로 등록하고, 그 단지에 신고가 거래가 수집되면 알림을 받게 한다. 지금 `/api/admin/*`(수집 실행, 지오코딩)는 인증 없이 열려 있다. 그래서 배포(7·8단계)를 하려면 먼저 인증을 붙여야 한다.

정할 것은 세 가지다.
- 로그인을 어떻게 유지하나 (세션 vs 토큰, 저장 위치)
- 무엇을 신고가라고 부르나
- 알림을 어디로 보내나

공통 원칙은 하나다. **로컬과 테스트에서 끝까지 돌릴 수 있는 것만 이번에 넣는다.** 외부 서비스(메일 서버, 소셜 앱 등록, HTTPS 도메인)가 있어야 하는 기능은 배포 뒤로 미룬다.

## 2. 결정 근거

### ① 서버 세션 vs JWT

| 후보 | 장점 | 단점 |
|---|---|---|
| **서버 세션 + HttpOnly 쿠키** (선택) | 로그아웃·강제 만료는 서버에서 세션을 지우면 끝난다. 토큰을 JS가 들고 있지 않아 XSS가 생겨도 세션 값을 훔쳐 가지 못한다 | 쿠키가 자동으로 실리므로 CSRF 방어가 필요하다. 서버가 상태를 갖는다 (②로 해결) |
| JWT (Access/Refresh) | 서버가 상태를 갖지 않는다. 다른 도메인·모바일 앱에 쓰기 좋다 | 발급한 토큰은 만료 전까지 유효하다. 즉시 로그아웃하려면 블랙리스트가 필요하고, 그러면 결국 서버에 상태가 생긴다. 토큰 저장 위치(localStorage면 XSS에 노출)도 따로 정해야 한다 |

프론트와 API는 같은 도메인이다 (개발은 Vite 프록시, 배포도 같은 호스트로 묶을 예정). 그래서 쿠키가 별도 설정 없이 따라간다. JWT의 장점인 "다른 도메인·여러 클라이언트"가 이 서비스에는 없다.

CSRF 방어는 Spring Security의 쿠키 기반 토큰을 쓴다. 서버가 `XSRF-TOKEN` 쿠키를 내리고, 프론트는 GET 이외 요청에 그 값을 `X-XSRF-TOKEN` 헤더로 다시 보낸다. 다른 사이트는 우리 쿠키 값을 읽을 수 없으므로 헤더를 만들지 못한다. SameSite=Lax는 다른 사이트에서 오는 POST에 쿠키가 실리지 않게 하는 두 번째 방어다.

로그인할 때 세션 ID를 새로 만든다 (세션 고정 공격 방지). 로그인 실패 문구는 하나("이메일 또는 비밀번호가 맞지 않습니다")로 한다. 없는 이메일과 틀린 비밀번호를 나누면 가입 여부가 드러나기 때문이다 (3. 한계).

### ② 세션 저장: PostgreSQL

| 후보 | 판단 |
|---|---|
| 서버 메모리 (기본값) | 서버를 재시작하면 모두 로그아웃된다. 8단계 k3s에서 파드가 2개면 요청이 다른 파드로 갈 때마다 로그인이 풀린다 |
| Redis | 빠르지만 지금 Redis가 없다. 세션 하나 때문에 인프라를 늘리지 않는다 |
| **PostgreSQL (Spring Session JDBC)** (선택) | 이미 있는 DB를 쓴다. 파드가 재시작되거나 여러 개여도 로그인이 유지된다. 요청마다 세션 조회가 하나 늘지만 PK 조회라 부담이 작다 |

세션 테이블은 Spring Batch 메타데이터(V4)처럼 Flyway로 만들고, 라이브러리의 자동 생성은 끈다 (스키마 변경은 Flyway로만, CLAUDE.md 규칙).

만료는 마지막 요청 후 7일이다. 송금·결제 같은 민감한 동작이 없는 조회 서비스라, 자주 다시 로그인하게 하는 불편이 더 크다고 봤다. 나중에 민감한 기능이 생기면 다시 정한다.

### ③ 가입: 자체 계정

카카오·구글 소셜 로그인은 외부 앱 등록과 콜백 URL이 필요하다. 그러면 로컬과 CI 테스트에서 끝까지 돌리기 어렵다. 이번엔 이메일 + 비밀번호 자체 계정만 두고, 소셜 로그인은 배포(도메인·HTTPS) 뒤에 검토한다.

비밀번호는 BCrypt로 저장한다. BCrypt는 사용자마다 다른 솔트를 붙이고, 일부러 느리게 계산한다. 그래서 DB가 유출돼도 미리 계산해 둔 표(레인보우 테이블)나 대량 대입으로 풀기 어렵다. SHA-256 한 번은 너무 빨라서 이 목적에 맞지 않는다. `DelegatingPasswordEncoder`를 쓰면 저장값 앞에 `{bcrypt}`처럼 방식이 붙으므로, 나중에 알고리즘을 바꿔도 기존 비밀번호를 그대로 확인할 수 있다.

이메일 인증과 비밀번호 찾기는 메일 발송이 있어야 해서 이번엔 빠진다 (3. 한계).

### ④ 관리자 계정과 관심단지 단위

- 관리자는 일반 가입 뒤 psql로 `role = 'ADMIN'`을 지정한다. 환경변수로 관리자를 자동 생성하면 비밀번호가 설정(k8s Secret 등)에 남는다. 수집 배치는 HTTP가 아니라 CLI(`batch` 프로필)로 돌기 때문에 인증과 상관없다
- 관심단지는 단지 단위다. 단지 × 면적으로 나누면 화면이 복잡해진다. 알림에 면적을 적어 주면 충분하다. 회원당 최대 50개로 제한한다

### ⑤ 신고가 규칙

**대상과 그룹**
- `valid_apt_trade` 중 `is_bulk = false`인 거래만 본다 (해제·missing·일괄 제외. ADR 007에서 요약·통계는 일괄 거래를 뺀다고 정했다)
- 그룹은 (`apt_seq`, `area_group`)이다. 면적이 다르면 가격을 비교할 수 없다

**정의**

거래 T는, 같은 그룹에서 T보다 **계약일이 이른** 거래가 1건 이상 있고, 그 최고가보다 T의 금액이 **크면** 신고가다.

**경계 사례**

| 사례 | 신고가인가 | 이유 |
|---|---|---|
| 그룹의 첫 거래 | 아님 | 비교할 이전 거래가 없다 |
| 이전 최고가와 같은 금액 | 아님 | 최고가를 "넘어야" 신고가다 |
| 같은 날 두 건, 둘 다 이전 최고가보다 비쌈 | 둘 다 신고가 | 같은 날 거래는 서로의 기준이 아니다. API가 계약일만 주므로 같은 날 거래의 순서를 모른다 |
| 이전 최고가가 일괄 거래 | 그 거래를 빼고 남은 최고가보다 크면 신고가 | 일괄 거래는 기준에 넣지 않는다 (ADR 007) |
| 이전 최고가 거래가 해제됨 | 그 거래를 빼고 남은 최고가보다 크면 신고가 | 유효 거래만 본다 |
| 이전 거래가 일괄·해제뿐 | 아님 | 빼고 나면 이전 거래가 없다 (첫 거래와 같다) |
| 판단한 뒤, 더 이른 날짜의 더 비싼 거래가 늦게 들어옴 | 기존 기록 유지 | 기록은 발견 당시의 스냅샷이다 (아래) |

**실행**
- 수집 Job의 지오코딩 step 뒤에 step을 하나 더 붙인다. 실행마다 최근 3개월 계약 거래를 판단한다. 거래 신고 기한이 계약 후 30일이라 새 거래는 대부분 이 안에 들어온다. 일일 수집은 최근 6개월을 다시 받지만(ADR 005), 몇 달 지난 거래를 이제 와서 "신고가"라고 알리는 것은 의미가 작다
- 결과는 `new_high_event`(거래 id unique, 이전 최고가, 발견 시각 `detected_at`)에 `INSERT … ON CONFLICT DO NOTHING`으로 넣는다. 같은 날 두 번 돌려도 중복 기록·중복 알림이 생기지 않는다
- 이 step이 실패해도 Job 종료 코드는 수집 step 기준을 따른다 (ADR 006, #18에서 지오코딩 step으로 겪은 문제와 같다)

**기록은 스냅샷이다**
- 한번 기록한 신고가는 나중에 조건이 바뀌어도 지우지 않는다. 사용자는 이미 알림을 받았고, 그 시점에는 맞는 판단이었다
- 거래가 나중에 해제·missing·일괄로 바뀌면, 기록은 두고 **보여줄 때** `valid_apt_trade`와 다시 조인해서 여전히 유효하고 일괄이 아닌 것만 보여준다
- 더 이른 날짜의 더 비싼 거래가 늦게 들어와도 기존 기록은 그대로다. 늦게 들어온 거래도 같은 규칙으로 따로 판단한다

**해제 뒤 늦게 잡히는 신고가 (의도한 동작)**

step은 매번 최근 3개월을 다시 판단한다. 그래서 이전 최고가가 나중에 해제되면, 그때까지 신고가가 아니던 거래가 그 뒤 실행에서 새로 신고가로 잡힌다. 이때 `detected_at`은 계약일이 아니라 새로 잡힌 날이다.

"높은 가격으로 계약을 신고해 시세를 띄운 뒤 해제하는" 일이 실제로 있다. 그 거래를 빼고 보면 다음 거래가 진짜 최고가이므로, 늦게라도 알리는 것이 맞다. 버그가 아니라 의도한 동작이다. 단, 늦게 잡히는 것은 판단 범위(최근 3개월 계약) 안의 거래뿐이다.

**SQL 방식**

**LATERAL 서브쿼리로 구현한다** (PR 6에서 비교해 정함). 판단 범위의 거래 T마다, 같은 그룹에서 계약일이 더 이른 비일괄 거래의 `max(deal_amount)`를 LATERAL로 구한다. T의 금액이 그보다 크면 `INSERT … SELECT … ON CONFLICT DO NOTHING`으로 넣는다.

로컬 DB(거래 374,692건, 최근 3개월 유효 거래 8,867건, 기준 2026-11-10)에서 두 쿼리를 `EXPLAIN ANALYZE`로 비교했다. 둘 다 같은 2,170건을 찾았다.

| | **LATERAL** (선택) | 윈도 함수 `MAX() OVER (PARTITION BY apt_seq, area_group ORDER BY deal_date RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW EXCLUDE GROUP)` |
|---|---|---|
| 실행 시간 | 2.38초 | 2.11초 |
| 읽는 범위 | 최근 거래마다 그 단지 이력만 인덱스(`apt_seq, deal_date`)로 읽는다 | 후보 단지의 전체 이력(27.8만 행)에 윈도를 계산한 뒤 바깥에서 최근 3개월만 남긴다. 정렬 두 번이 디스크로 넘쳤다(12MB, 18MB) |
| 데이터가 늘면 | 판단 범위(3개월)와 단지 이력 길이에 비례 | 전체 거래 수에 비례 (매달 커진다) |
| 뷰와의 관계 | `p.apt_seq = t.apt_seq` 조건이 `valid_apt_trade` 안의 `is_bulk` 윈도(PARTITION에 `apt_seq`)까지 내려간다 | 후보 단지를 `apt_seq IN (…)`으로 좁혀도 세미조인이라 뷰 안으로 내려가지 않는다. `is_bulk`를 전체 거래에 계산한다 |
| 규칙과의 대응 | "더 이른 계약일(`p.deal_date < t.deal_date`)의 최고가보다 크면"이 그대로 SQL이 된다 | 같은 날 제외를 `EXCLUDE GROUP` 프레임으로 표현한다. 프레임 문법을 알아야 읽힌다 |
| 이전 거래가 없을 때 | `max()`가 null → `>` 비교가 거짓 → 자동으로 제외 | 빈 프레임 → null, 같다 |

지금은 속도가 비슷하다. 그래도 LATERAL은 비용이 판단 범위에 비례하고, 규칙을 글자 그대로 옮긴 SQL이다. 관심단지 목록(PR 5)도 같은 패턴(`CROSS JOIN LATERAL` + `max`)을 쓴다. 판단 범위를 크게 늘리거나 전체 이력을 다시 계산해야 할 때는 윈도 방식이 유리해질 수 있다. 그때 다시 비교한다.

### ⑥ 알림 채널: 화면 안 알림

| 후보 | 판단 |
|---|---|
| **화면 안 알림** (선택) | 알림 목록 + 헤더의 안 읽음 개수. 외부 서비스가 필요 없다 |
| 이메일 | SMTP 서버, 발신 도메인 인증, 스팸 처리가 필요하다 |
| 웹 푸시 | HTTPS와 서비스 워커가 필요하다. 8단계 배포 뒤에나 가능하다 |

알림은 `notification` 테이블에 회원별 행으로 쌓는다. 신고가가 기록될 때 그 단지를 관심단지로 둔 회원에게 `INSERT … SELECT`로 행을 만든다 (쓸 때 나눠주기). 읽을 때는 회원 id로 바로 조회하므로 단순하다. 나중에 이메일·푸시를 붙일 때도 이 테이블을 읽어 보내면 되므로 판단 로직은 바뀌지 않는다.

## 3. 한계

- **"2020년 이후 최고가"다.** 수집 데이터가 2020-01부터라 그 전의 더 비싼 거래는 모른다. 화면 문구도 "신고가"가 아니라 "2020년 이후 최고가"로 쓴다
- **비밀번호를 잊으면 복구할 수 없다.** 이메일 인증·비밀번호 찾기가 없다. 메일 발송을 붙일 때 함께 넣는다
- **로그인 시도 횟수 제한이 없다.** 비밀번호 대입 공격을 막지 못한다. 배포 전에 점검한다
- **계정 존재 여부가 가입에서 드러난다.** 로그인 실패 문구는 하나로 통일했지만, 가입할 때 중복 이메일이면 409를 돌려주므로 그 이메일이 가입돼 있다는 것을 알 수 있다. 이를 막으려면 가입도 "메일을 확인하세요"처럼 같은 응답을 주고 메일로 안내해야 하는데, 메일 발송이 없다. 포트폴리오 범위에서는 받아들인다
- **관심단지 50개 제한은 동시 요청에서 조금 넘을 수 있다.** "개수 세기 → 넣기"가 한 번에 묶이지 않아서, 같은 회원이 동시에 여러 번 추가하면 51개가 될 수 있다. 한 사람이 자기 목록에서만 생기는 일이고 피해가 없으므로 허용한다

## 4. 범위 밖

| 항목 | 언제 |
|---|---|
| 소셜 로그인 (카카오·구글) | 배포(도메인·HTTPS) 뒤 검토 |
| 이메일 인증·비밀번호 찾기·이메일 알림 | 메일 발송을 붙일 때 |
| 웹 푸시 | 8단계 배포 뒤 |
| 회원 탈퇴 | 화면·API는 만들지 않는다. 관련 테이블은 회원 삭제 시 CASCADE로 준비만 해 둔다 |

## 5. 구현 기록

### 인증 (PR 3b)

- **CSRF는 `csrf.spa()`(Security 7.0+)로 켠다.** `XSRF-TOKEN` 쿠키(JS가 읽어야 하므로 HttpOnly 아님)를 요청마다 내려주고, `X-XSRF-TOKEN` 헤더 값과 비교한다. 헤더 없이 쿠키만 오면(다른 사이트의 폼 전송) 403이다
- **로그인은 `formLogin` 대신 JSON 컨트롤러(`POST /api/auth/login`)다.** API 문서와 `schema.d.ts`에 들어가게 하려는 것이다. 대신 필터가 해 주던 일을 직접 한다: 인증 → 세션 ID 변경(세션 고정 방지) → CSRF 토큰 교체 → SecurityContext를 세션에 저장 (Security 6부터 자동 저장 안 됨)
- **CSRF 토큰은 로그인 응답에서 바로 새로 준다.** `CsrfAuthenticationStrategy` 기본값은 옛 쿠키를 지우기만 하고 새 토큰은 다음 요청에서 내려준다. 그러면 로그인 직후 GET 없이 보낸 POST가 403이 된다. 토큰을 바로 꺼내도록 바꿨다
- **세션에는 작은 principal(`LoginMember`: id, email, role)만 둔다.** 비밀번호 해시는 인증 직후 지운다. PR 4에서 세션이 DB에 직렬화되므로 엔티티를 넣지 않는다
- **권한은 다음 로그인부터 적용된다.** 권한을 세션에 담기 때문에, psql로 `role`을 바꿔도 이미 로그인한 세션은 그대로다
- **규칙에 없는 경로는 `denyAll`이다.** 새 API를 만들고 규칙을 빼먹으면 열리는 대신 막힌다. 대가로 없는 경로도 404가 아니라 401(비로그인)·403(로그인)이다
- **보안 설정(`SecurityConfig`)과 `AuthController`는 웹 앱에서만 로드한다** (`@ConditionalOnWebApplication`). 배치 CLI는 웹 서버 없이 떠서 `HttpSecurity`가 없다. 처음엔 이 조건이 없어 배치 CLI가 시작하지 못했다 (docs/troubleshooting.md)
- **`/error`는 허용한다.** 컨트롤러 밖 오류는 `/error`로 다시 들어오는데, 막으면 원래 상태 코드 대신 401이 나간다
- **401·403은 필터에서 `SecurityProblemHandler`가 ProblemDetail(`application/problem+json`)로 쓴다.** 컨트롤러 밖이라 `ApiExceptionHandler`가 받지 못한다. 컨트롤러와 같은 Jackson 설정과 ProblemDetail mixin을 쓴다
- **세션 만료**는 이 PR에서는 서블릿 기본값(30분)이다. 7일과 DB 저장은 PR 4에서 함께 적용한다

### 세션 저장 (PR 4)
- **브라우저를 닫으면 로그아웃한다.** 공용 PC 보안을 위해 세션 쿠키에 유효기간(max-age)을 주지 않는다. 서버 세션은 마지막 요청 후 7일 뒤 정리된다
- **세션 테이블은 Flyway(V12)로 만든다.** Spring Session의 schema-postgresql.sql을 그대로 옮겼고, 자동 생성(initialize-schema)은 never로 끈다
- **세션 쿠키 이름이 JSESSIONID에서 SESSION으로 바뀐다.** Spring Session이 서블릿 세션을 대신하기 때문이다
### 신고가 판단 (PR 6)
- **`new_high_event`(V14)에는 거래 id, 이전 최고가, `detected_at`만 둔다.** 단지·면적·금액은 거래에서 얻는다. 보여줄 때 어차피 `valid_apt_trade`와 다시 조인하기 때문이다. 거래는 삭제하지 않으므로 FK에 CASCADE를 두지 않는다
- **판단 범위는 계약일 `baseDate − 3개월` 이후(그날 포함)다.** baseDate는 Job 파라미터다(없으면 서울 기준 오늘). 범위 밖의 거래도 이전 최고가의 기준으로는 쓴다
- **수집 step이 FAILED(한도 초과 등)면 이 step은 돌지 않는다.** 다음 실행이 같은 3개월을 다시 보므로 빠지는 거래는 없다
- **판단이 실패해도 tasklet이 예외를 잡아 COMPLETED로 끝낸다** (지오코딩 step과 같다). step은 `ResourcelessTransactionManager`로 감싸고, 트랜잭션은 `NewHighDetectService.detect()`의 `@Transactional`이 연다. step을 기본 트랜잭션 매니저로 감싸면 서비스 트랜잭션이 step 트랜잭션에 합류한다. 그러면 서비스 예외가 step 트랜잭션을 롤백 전용으로 만들어, 예외를 잡아도 step 커밋이 실패하고 Job이 FAILED(종료 코드 2)가 된다 (테스트로 확인)
- **PR 7 연결**: `detect()`의 트랜잭션에 알림 생성이 들어간다. `INSERT … ON CONFLICT DO NOTHING RETURNING`은 실제로 들어간 행만 돌려준다. 그래서 판단 INSERT를 `WITH inserted AS (… RETURNING id, trade_id)`로 감싸면, 이번 실행에서 새로 기록된 신고가에만 알림을 만들 수 있다. 이를 위해 판단과 기록을 한 문장으로 둔다
- 로컬 DB에서 처음 돌리면 최근 3개월 신고가가 한꺼번에 기록된다(2026-11 기준 약 2,170건). 알림은 PR 7부터라 이 백로그로 알림이 나가지는 않는다

### 알림 (PR 7)
- **알림(V15 `notification`)은 신고가 기록과 같은 문장에서 만든다.** 판단 INSERT를 `WITH inserted AS (… ON CONFLICT DO NOTHING RETURNING id, trade_id)`로 감싸고, 그 출력과 `watchlist`를 조인해 알림을 넣는다. `RETURNING`은 실제로 들어간 행만 돌려주므로 이번 실행에서 새로 기록된 신고가에만 알린다. 그래서 다시 돌려도 알림이 늘지 않고, PR 7 이전에 쌓인 기록이나 기록된 뒤 관심단지에 추가한 회원에게도 알림이 가지 않는다
- **WITH 안의 문장들은 같은 스냅샷을 본다.** 두 번째 INSERT에서 `new_high_event` 테이블을 다시 읽으면 방금 넣은 행이 보이지 않는다. 그래서 `inserted`의 출력을 쓴다. 알림의 FK 검사는 문장 끝에 하므로, 같은 문장에서 넣은 기록을 가리켜도 통과한다
- **단지로 관심 회원을 찾으므로 `watchlist(apt_seq)` 인덱스를 둔다.** PK `(member_id, apt_seq)`는 앞 컬럼이 `member_id`라 이 조회에 쓸 수 없다
- **목록·전체 수·안 읽음 수는 같은 숨김 조건을 쓴다.** 지금은 해제·사라짐·일괄이 된 거래의 알림은 셋 모두에서 빠진다. 배지 숫자와 목록이 어긋나지 않게 하려는 것이다. 알림 행은 지우지 않는다(스냅샷)
- **숨김 조건은 LATERAL 안에서 `valid_apt_trade`를 apt_seq·deal_date로 거르고 `LIMIT 1`을 둔다.** 뷰를 거래 id로만 조인하면 조건이 `is_bulk` 윈도(PARTITION BY sgg_cd, apt_seq, deal_date) 안으로 내려가지 못한다. 또 집계도 LIMIT도 없는 단순 서브쿼리는 플래너가 바깥 조인으로 끌어올려서, LATERAL로 써도 결국 같은 일이 생긴다. 로컬 DB(알림 50건)에서 목록 첫 페이지가 `LIMIT 1` 없이는 888ms(거래 35만 행에 윈도 계산, 디스크 정렬), 있으면 12ms였다. 관심단지 목록은 LATERAL 안이 `max()` 집계라 끌어올려지지 않는다
- **읽음 처리에서는 남의 알림도 없는 알림과 같은 404다.** `UPDATE … WHERE id = ? AND member_id = ?`가 0행이면 404를 준다. 그래서 다른 회원에게 그 id의 알림이 있는지 드러나지 않는다. 이미 읽은 알림은 `COALESCE`로 처음 읽은 시각을 둔다
- **한계: 모두 읽음은 요청 시점의 안 읽은 알림을 모두 바꾼다.** 화면을 연 뒤에 생긴 알림도 함께 읽음이 된다. 알림은 하루 한 번 배치에서만 생기므로 받아들인다
