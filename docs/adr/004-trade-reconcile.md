# 004. 거래 식별: 구×월 단위 대조(reconcile)

- 상태: 확정
- 날짜: 2026-10-25
- 관련: [ADR 002](002-trade-data-schema.md) 2-① "거래 고유 ID가 없다", [ADR 003](003-upsert-with-jdbc-template.md) (upsert·건수 계산·같은 키 병합을 대체), [키 충돌 분석](../analysis/2026-10-key-collision.md)

## 결정 요약

| 항목 | 결정 |
|---|---|
| 거래 식별 | 개별 레코드를 식별하지 않는다. 같은 키 그룹 안에서 **건수와 상태를 원본과 대조**한다 |
| 대조 단위 | 수집 단위인 구×월 전체 |
| 그룹 키 | 단지 + 계약일 + 전용면적 + 층 + 금액 (ADR 002 키를 유지하되 unique 제약은 없앰) |
| 대조 결과 | unchanged / updated / inserted / missing |
| 원본에서 사라진 거래 | 삭제하지 않고 `missing_since`로 표시 |
| 동시성 | 구×월 단위 advisory lock |
| 원본 완전성 | 건수 불일치는 1회 재시도 후 실패, missing이 대량이면 표시 보류 |
| 유효 거래 | `cancelled = false AND missing_since IS NULL` |

---

## 1. 배경

ADR 002는 `(단지, 계약일, 전용면적, 층, 금액)`을 unique 키로 잡고 upsert 하기로 했다. 이 조합이 겹칠 확률은 "매우 낮다"고 봤다.
4개 구 × 3개월(3,818건)에 적용해 보니 결과가 달랐다 ([분석](../analysis/2026-10-key-collision.md)).

- **302건이 82개 그룹으로 겹쳤고, 220건(5.8%)이 다른 레코드에 합쳐져 DB에 남지 않는다.**
- (a) 해제 후 재신고 50그룹(51건): 정상 레코드와 해제 레코드가 같은 키를 가진다. 해제된 레코드 76건 중 68%가 여기에 해당해서 흔하다.
- (b) 모두 정상 31그룹(168건): 대부분 일괄 매매다. 송파해링턴타워 한 단지의 170건이 17행만 남아, 송파 2026-09의 48.9%가 사라진다.
- (c) 재신고 때 거래 유형(`dealingGbn`)이 바뀐 1그룹: 불변이라고 생각한 필드도 재신고를 거치면 바뀔 수 있다.

이 분석에서 확인한 사실은 두 가지다.

1. **같은 키 레코드는 어떤 필드로도 영구히 구분할 수 없다.** (b)는 31그룹 중 30그룹이 모든 필드까지 같다. `aptDong`으로 구분되는 그룹은 0/31이다. API 응답 순서도 수집할 때마다 같다는 보장이 없다.
2. **그래도 건수는 정확히 보존해야 한다.** 일괄 매매 170건이 17건으로 저장되면 거래량·평균가가 모두 틀어진다.

그래서 "어느 레코드가 어느 행인가"를 맞히는 것은 포기한다. 대신 **같은 키 그룹 안에서 레코드 수와 각 레코드의 상태가 원본과 같도록** 맞춘다.

ADR 003 4절의 "정상 거래 우선 병합"은 재수집할 때 값이 뒤집히는 문제만 막는 임시 조치였다. 이 ADR이 그 조치를 대체한다.

## 2. 검토한 대안

### A. 그룹 대조 (reconcile) — 선택

같은 키 그룹 안에서 DB 행과 이번 응답 레코드를 짝지어, 같으면 그대로 두고 바뀌었으면 갱신한다. 남은 응답 레코드는 추가하고, 남은 DB 행은 표시한다.

- 장점: 건수가 원본과 같다. 짝이 지어진 행은 id가 유지된다. 무엇이 새로 들어왔는지, 무엇이 바뀌었는지, 무엇이 사라졌는지 알 수 있다. 값이 같으면 쓰기가 일어나지 않는다.
- 단점: 짝짓는 규칙을 직접 정하고 구현해야 한다. unique 제약이 없어지므로 동시 수집은 따로 막아야 한다. 같은 그룹 안에서 어느 호실이 어느 id인지는 임의로 정해진다.

### B. 구×월 전체 재적재 (DELETE 후 INSERT) — 기각

수집할 때마다 그 구·그 달의 거래를 모두 지우고 응답을 그대로 넣는다.

- 장점: 가장 단순하다. 짝짓기가 필요 없고 건수는 항상 원본과 같다.
- 단점
  - **거래 id가 수집할 때마다 바뀐다.** 관심 거래나 "신고가 알림을 보낸 거래"처럼 거래를 참조하는 데이터를 둘 수 없다. ADR 002에서 기각한 이유와 같다.
  - 무엇이 새로 들어왔고 무엇이 바뀌었는지 알 수 없다. 신규 거래·신고가 알림은 이 차이를 기반으로 한다.
  - `created_at`/`updated_at`이 의미를 잃는다.
  - 원본에서 사라진 거래의 기록이 남지 않는다.
  - 응답이 일부만 오거나 비어 있으면 그대로 데이터가 사라진다. 이를 막으려면 A의 완전성 가드와 같은 장치가 필요한데, 그러면 단순하다는 장점이 줄어든다.
  - 변경이 없어도 매번 그 달 전체를 지우고 다시 쓴다.

### C. 같은 키 안의 순번을 키에 추가 — 기각

`(기존 키, 그룹 안 순번)`을 unique 키로 쓴다. 분석 문서가 처음 제안했던 방향이다.

- 장점: unique 제약과 `ON CONFLICT` upsert를 그대로 쓸 수 있다.
- 기각 이유: 순번을 매길 기준이 없다.
  - 응답 순서로 매기면 순서가 바뀔 때 다른 레코드와 짝지어진다.
  - 값으로 정렬해서 매기면, 해제 레코드가 새로 끼어들거나 등기일이 채워지는 순간 정렬 위치가 바뀐다. 그러면 뒤 순번들이 한 칸씩 밀리면서 연쇄적으로 갱신된다. (a) 해제 후 재신고가 흔하므로 이 문제가 자주 생긴다.
  - 결국 순번을 안정적으로 매기려면 A처럼 기존 행과 대조해야 한다.

### D. 키에 필드 추가 — 기각

`aptDong`, `rgstDate`, `dealingGbn` 등을 키에 추가한다.

- 기각 이유
  - (b)는 31그룹 중 30그룹이 모든 필드가 같다. 추가할 수 있는 필드가 없다.
  - 동은 일괄 매매 단지에서 비어 있거나 건물 이름 하나로 똑같이 들어온다 (0/31).
  - 나중에 채워지는 값을 키에 넣으면, 값이 채워지는 순간 새 거래로 인식된다 (ADR 002).
  - (c)처럼 불변이라고 본 필드도 재신고로 바뀔 수 있다.

## 3. 결정

### ① 대조 규칙

필드를 세 종류로 나눈다.

- **그룹 키**: 단지, 계약일, 전용면적(소수 둘째 자리), 층, 금액
- **불변 필드**: 매수자 구분, 매도자 구분, 거래 유형, 중개사 소재지. 짝을 지으려면 값이 같아야 한다.
- **가변 필드**: 동, 등기일, 해제 여부·해제일. 나중에 채워지는 값이다.

구×월 응답 전체와 DB에 있는 그 구×월 행 전체(missing 행 포함)를 그룹 키로 묶는다. 그룹마다 다음 순서로 대조한다.

1. **unchanged**: 모든 필드가 같은 레코드와 행을 짝짓는다.
2. **updated**: 남은 것들 가운데 차이가 "빈 값 → 채워짐"으로 설명되는 쌍을 짝짓고, 행을 응답 값으로 갱신한다.
   - "설명된다"는 불변 필드가 같고, 가변 필드는 각각 같거나 DB 쪽이 비어 있고 응답 쪽이 채워진 경우를 말한다. 해제 여부는 정상 → 해제만 인정한다.
   - 이미 채워진 값이 바뀌거나 비는 경우는 설명되지 않는 것으로 본다. 이 경우 3·4단계로 넘어가 inserted + missing이 된다.
3. **inserted**: 짝이 없는 응답 레코드는 새 행으로 추가한다.
4. **missing**: 짝이 없는 DB 행은 삭제하지 않고 원본에서 사라진 것으로 표시한다 (③).

결과는 `inserted + updated + unchanged = 받은 레코드 수`가 된다. `missing`은 이번 수집에서 짝이 없는 DB 행 수다.

### ② 매칭 순서와 근거

같은 입력이면 항상 같은 결과가 나오도록 순서를 고정한다.

- **정확 일치를 먼저 짝짓는다.** "빈 값 → 채워짐" 관계는 추이적이라, 정확 일치를 먼저 짝지어도 최대 매칭 크기가 줄지 않는다.
  - 기호: **a ≤ b**는 불변 필드가 같고, 각 가변 필드는 a가 비어 있거나 b와 같다는 뜻이다 (해제는 정상 ≤ 해제). DB 행 r과 응답 레코드 x는 r ≤ x일 때 짝지을 수 있고, 정확 일치는 r = x다.
  - 근거: 정확 일치 쌍 (r, x)를 포함하지 않는 최대 매칭에서 r–x′, r′–x 쌍을 r–x, r′–x′로 바꾼다. r′ ≤ x = r ≤ x′이므로 r′ ≤ x′이고 r′–x′도 짝이 될 수 있다. 따라서 매칭 크기는 그대로다. r이나 x 한쪽만 짝이 있는 경우는 그 쌍을 (r, x)로 바꾸면 된다.
- **2단계는 최대 이분 매칭으로 짝짓는다.** 먼저 맞는 것끼리 탐욕적으로 짝지으면 짝이 덜 생길 수 있다. 예를 들어 동이 빈 행이 먼저 `101` 레코드를 가져가면, 이미 `101`이 채워진 행이 짝을 잃는다. 짝을 놓치면 같은 거래가 inserted + missing으로 기록되므로, 짝 수를 최대로 만든다.
- 정렬 기준
  - DB 행: missing이 아닌 행 먼저, 그다음 id 오름차순 (멀쩡한 행이 먼저 짝지어져 플래그 변경이 줄어든다)
  - 응답 레코드: 정상 거래 먼저, 그다음 필드 값 순 (빈 값은 뒤로)
- 결과적으로 해제 후 재신고에서 기존 행이 정상 레코드와도, 해제 레코드와도 짝지어질 수 있으면 **정상 레코드가 기존 id를 이어받는다.** 현재 유효한 거래의 id가 유지된다.
- 짝지어진 행이 missing 상태였다면 표시를 지우고 updated로 센다.

### ③ missing 플래그

- `apt_trade.missing_since`(TIMESTAMP, null 허용)에 원본에서 처음 사라진 것으로 확인된 시각을 기록한다. 이미 표시된 행은 처음 시각을 유지한다.
- 행은 삭제하지 않는다. 다음 수집에서 다시 짝이 지어지면 표시를 지운다. 일시적인 누락이면 이렇게 복구된다.
- unique 제약 `uk_apt_trade`는 없애고, 같은 컬럼 구성의 일반 인덱스로 바꾼다. 이 인덱스는 그룹 조회와 구×월 조회에 쓴다.

### ④ 동시성 제어

unique 제약이 없어지면 같은 구×월을 동시에 수집할 때 두 트랜잭션이 같은 레코드를 각각 insert 해서 중복이 생길 수 있다.

- 저장 트랜잭션을 시작할 때 구×월 값으로 PostgreSQL **트랜잭션 단위 advisory lock**(`pg_advisory_xact_lock`)을 잡는다. 같은 구×월의 두 번째 수집은 첫 번째가 커밋할 때까지 기다린 뒤, 커밋된 결과를 기준으로 대조한다.
- 잠금은 트랜잭션이 끝나면 자동으로 풀린다. 해제를 빠뜨릴 위험이 없다. 다른 구×월끼리는 서로 막지 않는다.
- API 호출은 지금처럼 트랜잭션 밖에서 한다. 잠금은 DB 저장 구간에만 걸린다.
- 단지 upsert(`ON CONFLICT DO UPDATE`)는 충돌한 단지 행을 잠근다(갱신 조건이 거짓이어도 잠근다). 같은 구의 다른 달처럼 단지가 겹치는 수집끼리 잠금 순서가 엇갈려 교착되지 않도록, 단지는 항상 `aptSeq` 순서로 쓴다.

### ⑤ 원본 완전성 가드

대조는 "응답이 그 구×월의 전체"라는 전제에 기대고 있다. 응답이 덜 오면 받지 못한 거래가 missing으로 잘못 표시된다. 그래서 두 가지 장치를 둔다.

1. **건수 불일치 → 1회 재시도 후 실패**
   - 받은 레코드 수가 응답의 `totalCount`와 다르면 대조하지 않는다.
   - 수집 중 새 신고가 들어오면 페이지를 받는 사이에 `totalCount`가 바뀔 수 있다. 그래서 처음부터 한 번 다시 받는다. 그래도 다르면 수집 실패로 처리하고 아무것도 저장하지 않는다.
   - 응답이 0건이면 대조하지 않는다. 장애나 일시 오류로 그 달 전체가 missing으로 표시되는 것을 막기 위해서다.
2. **missing 대량 발생 → 표시만 보류**
   - 보류 조건: `새 missing 건수 ≥ 최소 건수(기본 5)` **그리고** `새 missing 건수 / 기존 유효 행 수 > 비율 한도(기본 20%)`
   - 조건에 걸리면 missing 표시만 하지 않는다. 경고 로그를 남기고 수집 결과에 경고를 넣는다. inserted·updated는 그대로 반영한다. 응답에 있는 레코드는 믿을 수 있기 때문이다.
   - 최소 건수를 함께 보는 이유: 작은 구×월은 1~2건만 사라져도 비율이 한도를 넘는다. 비율만 보면 실제로 사라진 거래도 매번 같은 비율로 걸려 **영원히 보류**된다. 절대 건수 조건을 함께 두면 소수의 실제 삭제는 표시되고, 대량 이상만 보류된다.
   - 두 값은 환경변수로 조정할 수 있게 둔다.

### ⑥ 유효 거래 정의

**유효 거래 = `cancelled = false AND missing_since IS NULL`**

- 가격 추이, 신고가 판단 등 모든 조회는 이 조건을 기본으로 한다. 해제 거래와 원본에서 사라진 거래는 명시적으로 요청할 때만 포함한다.
- 구현 방식(뷰, 공통 조건 등)은 3단계에서 정한다.

## 4. 결과와 한계

**결과**
- 송파해링턴타워 170건이 170행으로 저장된다. 같은 데이터를 다시 수집하면 모두 unchanged다.
- 해제 후 재신고는 정상 행과 해제 행이 모두 남는다. 해제 기록이 보존되고, 유효 거래 조건으로 정상 거래만 조회된다.
- 재신고로 거래 유형이 바뀐 경우(c)는 기존 행이 해제로 갱신되고, 바뀐 유형의 정상 행이 추가된다.
- 응답 순서가 바뀌어도 결과가 같다.
- ADR 003의 "전후 행 수 차이로 건수 계산"이 필요 없어진다. 대조 결과에서 건수가 바로 나온다.
- 실측 (2026-10-25, 송파 2026-09, V1 방식으로 적재돼 있던 로컬 DB에서 2회 수집):

  ```json
  {"fetched":315,"complexes":80,"inserted":154,"updated":0,"unchanged":161,"missing":0,"warnings":[]}
  {"fetched":315,"complexes":80,"inserted":0,"updated":0,"unchanged":315,"missing":0,"warnings":[]}
  ```

  1회차 `inserted=154`는 분석에서 그 구·월의 "병합(손실)" 건수와 같다. 해링턴타워는 17행 → 170행이 됐다.

**한계**
- **같은 그룹 안에서 어느 호실이 어느 id인지는 임의다.** 예를 들어 일괄 매매 10건 중 1건만 해제되면, 어느 행이 해제로 바뀌는지는 정렬 규칙(가장 뒤 id)이 정할 뿐 실제 호실과는 관계없다. 원본에 구분할 정보가 없으므로 피할 수 없다. 그룹 단위 건수와 상태 분포는 정확하다.
- 이미 채워진 가변 값이 다른 값으로 바뀌면(예: 동 정보 정정) 같은 거래가 inserted + missing으로 기록된다. 유효 거래 건수는 맞지만 id가 바뀐다.
- 최소 건수 미만의 missing은 비율과 관계없이 표시된다. 예를 들어 기존 3행 중 2행이 일시적으로 빠져도 표시된다. 다음 수집에서 다시 짝이 지어지면 표시가 풀린다.
- missing 표시가 보류된 구×월은 이상 원인을 확인하기 전까지 사라진 거래가 유효 거래로 남는다. 수집 결과의 경고를 모니터링해야 한다.
- 응답 전체를 메모리에 올리고 대조한다. 구×월 단위(수백~천 건)에서는 문제가 없지만, 수집 단위를 키우면 다시 검토해야 한다.
- 모든 조회가 유효 거래 조건을 지켜야 한다. 빠뜨리면 해제·missing 행이 섞여 들어간다.

## 5. 재검토 조건

다음 중 하나가 생기면 이 결정을 다시 검토한다.

- API가 거래 고유 ID를 제공하기 시작할 때: 대조 없이 ID로 upsert 할 수 있다.
- 수집 단위를 구×월보다 크게 바꿀 때: 메모리 사용량, 잠금 범위, 완전성 가드의 기준을 다시 정해야 한다.
- missing 보류 경고가 자주 발생할 때: 비율 한도와 최소 건수가 실제 데이터에 맞지 않거나, 원본 쪽에 다른 누락 패턴이 있다는 신호다.
