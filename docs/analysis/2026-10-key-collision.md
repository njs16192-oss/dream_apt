# 거래 unique 키 충돌 분석 (2026-10)

- 작성일: 2026-10-22
- 관련: [ADR 002](../adr/002-trade-data-schema.md) 2-① "거래 고유 ID가 없다"
- 대상 데이터: 서울 강서구(`LAWD_CD=11500`), 계약월 2026-09 (`DEAL_YMD=202609`), 2026-10-22 조회

## 요약

ADR 002의 거래 unique 키 `(apt_seq, deal_date, exclu_use_ar, floor, deal_amount)`를 실제 API 응답에 적용해 보니, **252건 중 13건이 다른 레코드와 키가 겹쳤다** (충돌 그룹 12개, 관련 레코드 25건 → 239행으로 저장됨).
ADR 002에서는 "발생 확률이 매우 낮다"고 봤지만, 한 구·한 달에서 약 5%가 나왔다.

| 유형 | 그룹 | 관련 레코드 | 현재 키로 합쳐지는 건수 |
|---|---:|---:|---:|
| (a) 해제 후 재신고 | 1 | 2 | 1 |
| (b) 둘 다 정상인 다른 거래 | 11 | 23 | 12 |
| (c) 기타 | 0 | 0 | 0 |
| **합계** | **12** | **25** | **13** |

- (b)의 12건은 **실제 거래가 DB에서 사라지는** 손실이다. 그중 11건이 단지 하나(`11500-10189`)의 일괄 매매에서 나왔다.
- (a)는 지금 코드에서 정상 거래를 남기도록 처리했다 (아래 "현재 처리" 참고).
- 충돌한 25건 모두 `aptDong`이 비어 있었다. 동 정보로는 이 충돌들을 구분할 수 없다.

## 유형별 분석

### (a) 해제 후 재신고 — G1 (1그룹, 2건)

`11500-286` 명덕, 2026-09-17, 68.22㎡, 4층, 4억.

- 두 레코드는 `cdealType`/`cdealDay`만 다르다. 한 건은 해제(`O`, 해제일 26.10.02), 한 건은 정상.
- 이 단지의 9월 거래는 이 2건뿐이고, 중개사·거래 주체까지 같다.
- 해석: 계약(또는 신고 내용)을 해제 신고한 뒤, 같은 조건으로 다시 신고한 것으로 본다. 정상 레코드가 현재 유효한 거래다.
- 다른 호실 두 곳이 같은 날 같은 가격에 거래되고 그중 하나만 해제됐을 가능성도 완전히 배제할 수는 없다. 다만 단지 규모와 그달 거래가 이 2건뿐이라는 점에서 가능성은 낮다고 판단했다.

### (b) 둘 다 정상인 다른 거래 — G2~G12 (11그룹, 23건)

모든 필드가 **완전히 같은** 레코드들이다. API 데이터만으로는 "서로 다른 호실의 거래"인지 "같은 거래의 중복 레코드"인지 확정할 수 없어서, 정황으로 분류했다.

**G2~G11: `11500-10189` (50-5) — 10그룹, 21건 (확신도 높음)**
- 2026년 준공, 매도 `법인` → 매수 `공공기관`, `직거래`, 등기일 모두 26.09.16.
- 같은 날(9/9) 이 단지에서 **47건**이 거래됐다. 3층~14층에 걸쳐 21~29㎡ 소형 면적이 층마다 여러 건씩 있다.
- 해석: 공공기관이 신축 소형 주택을 통째로 사들인 일괄 매매(매입임대 등)로 보인다. 같은 층에 같은 타입·같은 가격의 호실이 여러 개 있으면 키가 겹친다. 47건이 모두 다른 호실이라고 보는 것이 자연스럽다.

**G12: `11500-8519` 더트루엘마곡HQ — 1그룹, 2건 (확신도 중간)**
- 2024년 준공, 매도 `법인` → 매수 `개인`, `직거래`. 9월 한 달 13건이 모두 같은 면적(48.3293㎡), 같은 거래 형태다.
- 분양가로 보이는 `59,900`이 여러 층에서 반복된다 (9/1·9/4·9/17 5층, 9/10·9/12 3층).
- 9/1 5층에는 이 2건 외에 67,400 거래(102동)가 하나 더 있다. 같은 날 같은 층에서 거래가 3건이므로 5층에 같은 타입 호실이 여러 개 있다는 뜻이다.
- 해석: 시행사의 잔여 세대 판매로, 같은 층·같은 타입·같은 분양가인 두 호실이 같은 날 팔린 것으로 본다. 다만 이 그룹은 G2~G11만큼 정황이 강하지 않아서, API 쪽 중복 레코드일 가능성도 남는다.

### (c) 기타 — 없음

## 키 보완 시 고려할 점 (다음 PR 논의용, 구현 전)

이번 분석에서 확인된 사실만 정리한다. 구체적인 키 설계는 다음 PR에서 ADR 004로 정한다.

1. **(b)는 API의 어떤 필드로도 구분할 수 없다.** 키에 필드를 추가하는 방식(동, 등기일 등)으로는 해결되지 않는다. 같은 키 안의 순번처럼 "몇 번째 레코드인가"를 담는 방식이 필요해 보인다.
2. **(a)를 구분하는 필드(`cdealType`)는 나중에 채워지는 값이다.** 이 값을 키에 넣으면, 정상 거래가 해제되는 순간 새 거래로 인식되는 ADR 002의 원래 문제가 다시 생긴다.
3. 순번 방식을 쓰면 API 응답 순서가 수집할 때마다 달라질 때 같은 행이 다른 레코드와 짝지어질 수 있다. (b)처럼 완전히 같은 레코드끼리는 문제가 안 되지만, (a)처럼 늦게 채워지는 값이 다른 경우에는 짝짓는 규칙을 정해야 한다.
4. 표본이 한 구·한 달뿐이다. 키를 정하기 전에 다른 구·다른 달(특히 신축 일괄 매매가 많은 지역)로 빈도와 유형을 더 확인하는 것이 좋다.

## 현재 처리 (이번 PR)

키는 그대로 두고, 한 번의 수집 안에서 키가 같은 레코드를 정해진 규칙으로 하나로 합친다 (`TradeUpsertService.mergeSameKey`).

- 우선순위: 정상 거래(`cancelled=false`) → 등기일 있음 → 동 있음 → 값 순. API 응답 순서와 관계없이 항상 같은 레코드가 남는다.
- 합친 건수는 수집 응답의 `merged`로, 그룹별 내역은 WARN 로그로 남긴다.
- 효과: 같은 데이터를 다시 수집해도 값이 뒤집히지 않는다 (합치기 전에는 재수집할 때마다 `updated=2`). G1은 정상 거래로 저장된다.
- 남은 한계: (b)의 12건은 여전히 1건으로 합쳐져 저장되지 않는다.

실측 (같은 구·월 2회 연속 수집):

```json
{"fetched":252,"complexes":108,"inserted":0,"updated":1,"unchanged":238,"merged":13}
{"fetched":252,"complexes":108,"inserted":0,"updated":0,"unchanged":239,"merged":13}
```

1회차의 `updated=1`은 이전 코드에서 해제로 덮였던 G1이 정상 거래로 복원된 것이다.
